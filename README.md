# 崩坏学园2 小助手

基于 [MaaFramework](https://github.com/MaaXYZ/MaaFramework) 的崩坏学园2 自动化助手：
图像识别 + 模拟点击，跑在 PC 上控制安卓模拟器 / 真机。

本项目从官方模板 [MaaPracticeBoilerplate](https://github.com/MaaXYZ/MaaPracticeBoilerplate)
clone 出来改，所以目录结构、JSON Schema、校验工具都是官方那一套，上游更新可以直接跟。

## 上手四步

### 1. 装环境

```sh
# 模拟器：MuMu 12（本机在 E:\MuMu Player 12）
# adb 直接用模拟器自带的那份：E:\MuMu Player 12\shell\adb.exe（tools 里已内置这个路径）
pip install maa-framework          # agent 进程和客户端都靠它
pip install pillow                 # 可选，tools/capture.py 裁模板用

python tools/check_env.py          # 自检：分辨率、设备、pipeline 引用、缺哪些图
```

**分辨率是 1280x720 横屏**（短边 720）。`interface.json` 里 `display_short_side: 720`
就是按短边缩放，全部 roi 都写在这个坐标系下。

⚠️ 一个坑：`adb shell wm size` 报的是**面板物理尺寸**（MuMu 12 会报 `Physical size: 720x1280`），
模拟器把显示覆盖成横屏时它会骗人。自检脚本直接量一张截图的像素头，那才是 MaaFramework 看到的东西。

**adb 连不上时**：MuMu 的 adb 端口默认 16384（第二个实例 16416，往后 +32）。
`tools/` 里的两个脚本会在没设备时自动 `adb connect 127.0.0.1:16384`，手动排查就是：

```sh
"E:\MuMu Player 12\shell\adb.exe" connect 127.0.0.1:16384
"E:\MuMu Player 12\shell\adb.exe" devices
```

> `assets/MaaCommonAssets` 是官方模板带的子模块（OCR 模型），当前没拉下来。
> 本项目的流程暂时不用 OCR，需要时执行：
> `git submodule update --init --recursive`

### 2. 采模板图（最花时间的一步）

先把游戏开到**首页**，然后：

```sh
python tools/capture.py devices        # 确认连上了
python tools/capture.py shoot          # 截一张全屏到 image/_raw/
python tools/capture.py list           # 看还缺哪张、每张长什么样、建议 roi
python tools/capture.py crop 首页/出击.png 60 380 220 90
```

`crop` 的 `x y w h` 按 **1280x720 坐标**给。想要能拖动框选的可视化工具，用
MaaFramework 自带的 ImageCropper，或者直接上 **MaaDebugger**（能单步跑流水线、
把识别框画在截图上，调 roi 全靠它）。

裁图的几条经验：

- 只截那一处**独特的图案**，别把会变的数字、体力条、光效截进去；
- 别裁太大（大图匹配更慢更容易误命中），也别太糊；
- 返回箭头这种全游戏通用的只截一次，每个界面单独截是浪费。

### 怎么精确定位一个按钮的坐标（踩过坑）

这是我实际踩出来的教训，按可靠性从高到低：

1. **按颜色在像素级找**（最准）。按钮通常是纯色圆角矩形，用 numpy 按颜色扫一遍再聚类，
   拿到的是精确到像素的包围盒。找「快给我下」就是这么找到的：`x 436..629, y 430..482`。
2. **按比例换算**。预览图尺寸和原图尺寸是等比缩放的，量出预览里的像素再乘系数，
   误差通常在几个像素内。
3. ~~看坐标网格用眼睛读~~ —— `capture.py shoot --grid` 画出来的网格**看着方便但会读错**，
   我照着网格读按钮位置，结果整整差了一格（100 像素）。
   网格适合判断「大方向在左上还是右下」，不适合定精确坐标。

拿到包围盒之后，用 `crop` 从原图裁，**裁完一定回头看一眼那张图**是不是真的框住了目标 ——
`python tools/capture.py crop _raw/检查.png <x> <y> <w> <h> --from <原图>`，
比自己反复描述快得多。

### 裁完必须实测打分（这一步能救命）

眼睛看着"应该能认出来"是不可靠的。用 OpenCV 实测：

```sh
python tools/check_template.py 首页/出击.png --live 6
```

`--live 6` 会连拍 6 张同一个界面再逐个匹配，输出分数和**抖动**：

| 分数 | 含义 |
| --- | --- |
| ≥ 0.95 | 很稳，threshold 可以放 0.85 |
| 0.85 ~ 0.95 | 能用，threshold 放 0.80 |
| < 0.85 | 不可靠，重裁 |

**抖动（最高分 - 最低分）比分数更重要。** 抖动小 = 这块是静态的；
抖动大 = 模板里混进了会动的东西（Live2D 动画、光效、数字、进度条），换个静态锚点。

实战例子，标题页那两张：

| 模板 | 分数 | 抖动 | 结论 |
| --- | --- | --- | --- |
| 右上角「账号切换」按钮 | 0.979 ~ 0.994 | 0.015 | ✅ 拿它当锚点 |
| 中下方「抚摸屏幕继续」文字 | 0.609 ~ 0.904 | 0.296 | ❌ 文字在闪，废掉 |

所以 `启动_标题页` 节点是**认「账号切换」、但点 `(640, 670)`**（`target` 字段填固定坐标点
就能把「识别锚点」和「点击位置」分开），而不是直接点认到的东西。

> 另外注意：模板"不在场"时分数自然很低（约 0.4 左右），这不算模板坏了。
> 比如「快给我下」只在资源缺失时出现，平时打分低是正常的。

### 3. 核对包名

**官服已经核实过了**：`com.miHoYo.HSoDv2Original`（已写进 `interface.json`，不用改）。
只有你要跑 B服 / 日服 时才需要自己查：

### 4. 跑起来（要图形界面就跑这条）

本项目是个 **PI v2 资源包**。想要 MAA 那种"勾任务 → 开始"的界面，不用自己写 UI：
官方通用 GUI **MFAAvalonia** 能直接吃 `interface.json`。一条命令组装好：

```sh
python tools/get_gui.py
```

它会下 `MaaFramework v5.13.0`（原生库）和 `MFAAvalonia v2.16.1`，按官方模板 CI
（`.github/workflows/install.yml`）的布局拼出一个 `gui/` 目录，然后：

```
双击 gui/MFAAvalonia.exe
```

要求：**.NET 10 Runtime**（本机已装 10.0.1）。首次下载约 170 MB，之后会跳过。

第一次进去它会自动做资源检测、控制器检测、拉起 agent 进程。本机的 MuMu 12 它**会自动认出来**
（adb 路径和 `127.0.0.1:16384` 都自动填好，截图模式用 MuMu 专属的 EmulatorExtras），
一般不用手动配。之后勾任务 → 开始就行。

改完 pipeline 或补了新模板图，同步过去：

```sh
python tools/get_gui.py --sync-only     # 只同步 assets/ 和 agent/，不重新下载
```

其它选择：

- 命令行：[MaaPiCli](https://github.com/MaaXYZ/MaaFramework)
- 另一个通用 GUI：[MXU](https://github.com/MistEO/MXU)（Tauri 写的，目录约定和 MFAAvalonia 不同，
  它要 `mxu.exe` + `maafw/` + 根目录 `interface.json` + `resource/`）
- 开发调试：MaaDebugger（调 roi 用它，能单步跑流水线并把识别框画在截图上）

跑之前记得：**游戏停在首页**、**套装换成自动套**（见下面配装要求）。

## 自动战斗怎么调

核心在 `agent/battle_config.json`，改完不用重新编译：

| 字段 | 含义 |
| --- | --- |
| `attack_button` | 攻击键坐标。崩崩的武器键在屏幕右下 |
| `attack_jitter` | 点击随机抖动像素，避免每次都点同一个点 |
| `click_interval` | 两次点击的间隔（秒） |
| `joystick_center` | 左下摇杆中心坐标 |
| `walk_left_offset` / `walk_right_offset` | 从摇杆中心往左 / 右拖多远（负数往左） |
| `walk_duration_ms` | 拖动耗时，太短游戏不认 |
| `walk_hold_ms` | 拖完之后不动的时长，用来持续走路 |
| `swipe_every` | 每点 N 次攻击就走位一次 |
| `pause_every` / `pause_seconds` | 每 N 次点击随机停顿一下，别太机械 |
| `fail_limit` | 连续点击失败多少次就放弃 |

界面上的「单次战斗时长」只覆盖 `duration`，不会把你调好的坐标冲掉。

**为什么按时间而不是认图？** 崩崩战斗里没有稳定的「打完了」标志物（血条、结算画面都在动），
按时间跑最稳。时长按你刷的图调：太短这关没打完就去点「再次挑战」了，太长会在结算界面空转。
默认 60 秒。

刷关能不能跑通，一半看脚本一半看你的号：

## 游戏机制要点（踩过的坑，改流程前先看）

这些是实测出来的，不知道就会白写：

- **导航栏选中的标签是白底。** 首页/战斗/装备/商店/社交/其他 六个按钮，当前选中的那个会变成白底高亮，
  按暗度做像素分析**永远扫不到它**（我就是这么把点击坐标算错的）。
  所以点导航只能靠实测坐标（`654/766/879/991/~1105/1218`，y=60），别指望识别。
- **文字会呼吸闪烁。** 标题页的「抚摸屏幕继续」实测抖动 0.296，当模板不可靠；
  标题页请用静态的「账号切换」按钮当锚点（抖动 0.015），再点固定坐标继续。
- **主界面是 Live2D，角色和背景一直在动。** 左上角玩家信息板（`通用/主界面.png`）是静态的，
  全项目的"我在主界面吗"都靠它 —— 换头像或改名要重截。
- **同一种文字在不同稀有度下颜色不同。** 使魔探险的「点击领取奖励」S 橙 / A 紫 / C 绿，
  一张模板认不全，得按颜色各裁一张，然后一起塞进节点的 `template` 数组。
- **同屏有多个相同文字时**（比如好几个「点击领取奖励」），识别会命中第一个，
  用 `max_hit` 反复点、每点一次列表往上顶一个，就能全领完。领完记得判断终止条件，
  否则会一直点空气。
- **「网络连接中…」很常见**，是游戏自己的问题，等它消失就行（`通用_等网络连接` 节点就是干这个的），
  不要当故障处理。
- **使魔探险是「领奖励 + 派遣新一批」两件事。** 只领不派，第二天就没有已完成的任务可领了。
- **派遣一次实际只点三下**：点「点击选择使魔」→ 进选择使魔界面 → 点「一键派遣」→ 点「出发」。
  「一键派遣」是游戏自己给的，它会自动把 4 个使魔槽填满、特性全部凑齐（实测成功率直接到 100.00%），
  所以**根本不用自己挑使魔**。点完「出发」直接回列表，**没有二次确认弹窗**。
- **列表里「已完成待领取」和「未接取」是两种行**：前者右边是「点击领取奖励」（S 橙 / A 紫 / C 绿，
  每个稀有度一张模板），后者右边是「点击选择使魔」（灰字，各等级共用一张）。所以顺序是先把奖励领干净，
  再挨个派遣 —— 派完的行会变成「剩余时间 xx:xx:xx」留在列表里。
- **「找不到可以派遣的了」是干完了，不是失败。** 这时候流程要能干净地退出去（点返回箭头回主界面），
  别留在面板上等识别超时。
- **roi 必须把模板整个装下，差一点点就全废。** 「返回箭头」模板是 80x68、实际贴在 (20,102)，
  而 roi 原来写的是 `[0, 0, 240, 160]` —— 模板下缘伸到 y=170，超出 roi 10 个像素，OpenCV 就直接不匹配，
  实测只有 0.29（同样一张图全屏匹配是 0.99）。**这种"差一点"的 roi 不报错、不警告，只是永远认不到**，
  于是所有「退一步 / 回主界面」的兜底全部静默失效。全部改成 200 高就正常了。
- **「我在主界面吗」不能用左上角信息板判断。** 任务面板、商店这些子界面**顶部 UI 是同一套**，
  左上角玩家信息板照常显示，拿它当锚点的话在任务面板里也命中 0.97 —— 该退的界面一步都不退。
  现在改用「返回箭头在不在」判断（`inverse: true`）：子界面有箭头就要退，主界面认不到箭头才算到家。
- **`next` 里所有节点都认不到时会死等到 20 秒超时，把整个任务判成失败。** 所以每个 next 列表末尾
  要留一个**必然能命中**的节点兜底，别让流程最后那一下白卡 20 秒。
- **`agent/main.py` 不能拿 `sys.argv[-1]` 当 socket_id。** MFAAvalonia 实际传的是
  `main.py kvZafnuL socket_id=kvZafnuL instance_id=default instance_name=配置 1` ——
  最后那个 `instance_name` 里**带空格**，会被拆成两个参数，于是 `argv[-1]` 拿到的是 `1`。
  agent 拿着错的 id 去连 socket，永远连不上，界面就一直卡在「正在启动 Agent」，
  但进程其实活着（任务管理器里能看到 python）—— 这个组合最容易误判成"agent 启动慢"。
  改成按优先级找：`socket_id=xxx` > 第一个位置参数 > 最后一个参数。
- **`input` 类型的字段别声明成 `pipeline_type: "bool"`。** MFAAvalonia 只接受 `true` / `false`
  （区分大小写），输入框里填 `1` 会直接报 `String '1' was not recognized as a valid Boolean`，
  而让人手敲 `true`/`false` 又太别扭。**声明成 `int`、填 `1`/`0`**，agent 那边 `bool(int(x))`
  一样能拿到布尔值。
- **列表翻页别让节点在 next 里指回自己。** 那样只要视口里没目标就会一路往下滑，滑到底还在滑
  （实测被当场叫停）。挂一次就够：滑一次约 370px，够露出下一屏。
- **`max_hit` 在这个框架版本里根本不起作用。** 原来「模块跑完回调度器、靠 `max_hit` 跳过已完成的模块」
  那套写法会打成死循环 —— 实测日志里 `list=["测试_A","测试_B"]` 中那个已经命中过的节点照样被反复执行。
  现在改成**单向链式调度**：`日常_开始 → 日常_步骤2 → … → 日常_步骤7`，每个模块有自己的收尾节点，
  收尾退回主界面后直接进下一步。没勾的模块会被 `enabled: false` 跳过，链子照样往下走。
- **战斗页有三个 tab（主线 / 活动 / 挑战），日常只关心「活动」。** 而且点「战斗」导航
  **不保证**落在活动卡片列表上：游戏会记住你上次停在哪个活动子页（比如虚轴之庭），
  那时整页被子界面盖住，左边根本没有 tab 栏。所以流程要先认一下「我是不是站在某个活动子页里」。
- **活动卡片每次轮换都换名字，别拿活动名当模板。** 它的稳定特征是卡片右上角那两个标签：
  「难度指数：B」和「剩余时间：xx天」，活动 BONUS 模块就靠这两张认当期活动。
- **这类刷刷刷活动的关卡入口就在活动页左上角**，固定坐标点过去就行 —— 不用每次活动都重新截图。
  万一那页没有，翻一页再点一次（活动地图右箭头到底了会变灰，翻多了也不会绕回第 1 页）。
- **活动 BONUS 关没有「快捷战斗」，只能走「选择助战好友」手动进本**（消耗体力 50）。
  好友列表第一张卡默认就是选中的那个，点它进助战确认页，再点「开战」。
- **「这一把打完了」的判据是认「战斗结算」标题。** agent 的 `bonus_battle` 边打边每 3 秒截一张图认它，
  认到立刻收工 —— 套装强的话十几秒就结束，不用傻等到时间上限。
- **活动 BONUS 的「刷 N 轮」循环写在 agent 里，不是 pipeline 里。** 一开始我用「预生成 12 轮节点 +
  用 enabled 挑前几轮」来实现次数，但那样用户只能从固定档位里挑。正确的做法是
  pipeline 只留一轮（`开战 → 打完 → 收尾`），把循环交给 `bonus_battle`：
  它自己数着刷 N 轮，每轮打完判断该继续还是收工。**轮数想填多少填多少。**
- **多个选项改同一个 `custom_action_param` 会互相覆盖。** MaaFramework 合并 `pipeline_override` 时
  是「同名字段后者覆盖前者」，而「刷几次 / 怎么打 / 用水晶」这三个开关最终都落在同一个
  `custom_action_param` 对象上 —— 拆成三个选项的话只有最后一个生效。所以做成了**一个 `input` 选项**
  （`type: "input"` + `inputs[]` + 用 `{名称}` 占位符引用），三个字段一次填完。
- **体力用完时「再次挑战」会变红**，红色状态的按钮认不出来（模板是正常态），
  于是流程会自动转去处理体力弹窗（兑换双倍体力 / 水晶补体力），真没得换了才点「结算确定」收工。
- **体力不足会弹「兑换双倍体力」窗**，正文写「主人可兑换75双倍体力，补充150体力」，按钮是
  **「兑换 / 取消」**（注意不是「确定」）。弹窗居中，所以「兑换」按钮相对标题的偏移固定，
  用 `target_offset: [-168, 199, 0, 0]` 从标题偏过去，比写死屏幕坐标稳。
  ⚠️ **裁这张模板要把截图先缩到 1280x720 再裁** —— 用户给的全屏图是 1467x825，
  直接按原图裁尺寸就错了（我第一次就踩了这个，拿弹窗局部图当尺寸算偏移，算出来是歪的）。
  **这一步普通日常就走，不用额外勾** —— 存的体力不用白不用，刷到真的没得换为止。
- **「一直刷」是另一回事：水晶换体力。** 那个窗标题是「补充体力」，正文「主人可花费60水晶，补充205体力」，
  按钮 **「购买 / 取消」**。同一套写法：`target_offset: [-111, 200, 0, 0]` 从标题偏到「购买」。
  这步只在 GUI 选了「一直刷」时才执行 —— 不选的话弹出来也不管，直接收工。
  注意两个窗的标题宽度不一样（一个 5 字一个 4 字），所以 offset 必须各算各的，不能复用。
- **活动子页的返回方式：点右上角那个活动名字。** 虚轴之庭、崩坏之塔这类全屏子页
  **没有返回箭头**，导航栏也点不动，只有右上角的活动名标签（约 (1080,140)-(1220,190)）能返回。
  ⚠️ 另外这些页面按系统返回键是**弹「确认退出游戏」**，别按。
- **「快捷战斗」是扫荡，不是进战斗。** 点了会弹一个数量选择窗（默认 2 次，另有一个 Max），
  确定后直接出结算页，再点结算页的「确定」回关卡详情。**「选择助战好友」才是手动进本**，别点错。
  虚轴之庭的 BOSS 有多阶段，一次扫不完，所以那两个模块各写了三轮
  （点快捷战斗 → 确定 → 结算确定），哪一轮认不到按钮就提前收尾。
- **多元裂缝那张卡片在右列偏下，得在右侧拖列表才滚得动**（在左列拖会被卡片吃掉，滑动无效）。

## 交付前必须真跑一次（这一步抓到过真 bug）

`python tools/validate_schema.py` 过、我自己的 `check_env.py` 也过，**都不代表框架能跑起来**。
只有让 MaaFramework 本体加载一次资源才算数：

```sh
python tools/run_once.py 主界面_就绪
```

它会真的加载 `assets/resource`、真的连 adb、真的在实时画面上跑一次识别，输出类似：

```
资源加载 OK
已连接
- 主界面_就绪: 命中  Rect(x=18, y=12, w=245, h=45)
```

实测抓到过两个只有真跑才暴露的问题：

1. **`target` 字段必须是 4 个元素。** PI 协议的 schema 文档写着 `array<int, 2>` 合法，
   但 MaaFramework v5.13.0 的 `parse_rect` 要求 `size == 4`，写 `[640, 670]` 直接
   让整个资源加载失败（`parse_click failed to parse_action_target`）。
   正确写法是区域矩形 `[x, y, w, h]`，框架会在矩形内随机取点 —— 顺带更像人手。
2. **`next` 引用不存在的节点会让加载整体失败**（`Invalid next node name`），
   不是运行时才报。删节点的时候记得全局搜一遍谁在引用它。
3. **识别不到和 roi 写错，从日志里长得一模一样。** 使魔探险整条流程跑完，日志里
   每个节点都「命中」，看起来完美 —— 但最后收尾那步一直卡到 20 秒超时、任务判失败。
   原因就是「返回箭头」的 roi 少了 10 个像素（模板比 roi 高一点，OpenCV 直接不匹配）。
   **判据是：拿同一张实时截图，同时用 `check_template.py` 全屏测一遍、
   再用节点里的 roi 测一遍，两边分数对不上就是 roi 的问题。**

顺便：日常模块在 pipeline 里默认是 `enabled: false`，靠 GUI 勾选时才 override 成 true。
命令行想直接测没勾过的模块，用 `--enable`：

```sh
python tools/run_once.py 日常_使魔探险_开面板 --enable 日常_使魔探险_开面板,日常_使魔探险_已在页,日常_使魔探险_切页,日常_使魔探险_领取,日常_使魔探险_派遣,日常_派遣_一键派遣,日常_派遣_出发,日常_使魔探险_翻页,日常_使魔探险_收尾
```

⚠️ 这条命令会**真的点**。它会从「打开任务面板」一路跑到派遣完、退回主界面，
是验证整条日常链路最直接的办法，但别在不想让它动手的时候跑。

## 流水线是怎么串起来的
MaaFramework 的 `next` 是**按顺序识别、只执行第一个命中的**，所以本项目大量用三种写法：

- **兜底返回**：`"next": ["回到首页", "回到首页_退一步"]` —— 先认出首页就结束，
  认不到就点返回箭头，点完再判断一次，一直退到首页为止。
- **跑一次就跳过**：模块节点写 `"max_hit": 1`，用掉之后在别的节点的 next 列表里会被自动跳过。
  `日常_开始` 就是靠这个从 8 个模块里挨个往下推，最后落到 `日常_收尾`。
- **循环计数**：`刷关_战斗一次` 的 `max_hit` 就是「刷关次数」，界面选项改的就是它，
  用完自动跳到收尾，不会无限刷。

节点被跳过、识别不到都会记在日志里，调流程时优先看日志。

## GUI 里的任务怎么切的

任务列表长这样，每个都能单独跑：

```
启动崩坏学园2 / 自动战斗 / 重复刷关
关卡战斗                        ← 整条链：邮件 → 使魔探险 → 商店 → 虚轴之庭 → 使魔的爱 → 活动BONUS → 存在感
使魔探险 / 商店购物 / 领取奖励    ← 从上面那条链里拎出来的单个模块，随时单独跑
```

后三个模块任务**复用同一套 pipeline 节点**，只是在自己的 override 里把那个模块的
**收尾节点的 `next` 改成 `日常_收尾`** —— 这样单独跑完就结束，不会顺着调度链继续往下跑
（`next` 是可以在 override 里覆盖的）。节点名保持 `日常_xxx` 没动，那是 pipeline 内部标识。

⚠️ **多个选项改同一个 `custom_action_param` 会互相覆盖**（合并规则是「同名字段后者覆盖前者」）。
「碎水晶」就是这么处理的：它和「BONUS设置」都要影响 `bonus_battle` 的参数，所以单独拆了一个
`日常_活动BONUS_打完_水晶` 节点，开战时两个都放进 next、水晶版排前面 —— 勾了就命中水晶版，
没勾就被跳过、命中普通版。

## GUI 加载失败时的替代方案：`tools/run_task.py`

这台机器上 **MFAAvalonia 会加载资源失败**（日志里
`IMaaResource failed to load resources. MaaJobStatus cannot be Failed.`，
界面提示「资源加载失败！请删除整个文件夹重新下载」），但**同一份资源用 MaaFramework
本体加载是好的** —— `deps/bin/MaaPiCli.exe` 能正常解析 `interface.json` 并列出任务。
所以这是客户端自己的问题，不是资源坏了。

绕开它用这个：

```sh
python tools/run_task.py                    # 列任务
python tools/run_task.py 重复刷关            # 跑一个任务（自动套用默认选项）
python tools/run_task.py 重复刷关 --option 次数=3
python tools/run_task.py --node 主界面_就绪   # 直接跑节点
python tools/run_task.py --node 主界面_就绪 --no-agent   # 不拉起 agent
```

它会自己按 GUI 的规则展开选项（select/switch/checkbox/input 四种类型，
`{占位符}` 按 `pipeline_type` 转 int/bool/string），然后加载资源、连 adb、
**拉起 agent 子进程并连上它**，最后跑任务。

`--option` 的键是 **input 字段名**（比如「次数」），不是选项名（「刷取次数」）——
先 `python tools/run_task.py` 看一眼，或者去 `interface.json` 里查 `inputs[].name`。

**拉起 agent 有两个坑**（都是实测踩出来的）：

1. `AgentClient.connect()` **必须先 `bind(resource)`**，否则直接报
   `resource is not bound` 然后失败——不是超时，是立刻失败。
2. agent 的 identifier **别依赖自动生成**：`AgentClient()` 不传参时
   `client.identifier` 有时返回 None，那样 agent 子进程拿到空 id，永远连不上。
   显式传一个随机字符串最稳。
